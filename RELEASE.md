# Banana Slides RU Desktop Release and Update Specification

This fork keeps the existing desktop release pipeline in `.github/workflows/release-desktop.yml` and `desktop/electron-builder.yml`. The workflow is drafted only; this work order does not publish, trigger, or write to GitHub.

## Version and tags

Use semver-compatible versions with the Phase 1 base and Russian fork suffix:

```text
desktop/package.json: 0.9.0-rc.7-ru.1
Git tag:               v0.9.0-rc.7-ru.1
```

Increment `ru.N` for each fork release based on the same upstream base. `update-policy.js` removes a leading `v` and compares the complete semver prerelease, so `0.9.0-rc.7-ru.1` is newer than `0.9.0-rc.7`. Keep a prerelease suffix while the fork is on the release-candidate channel; a stable release must use a normal semver version and will not consume prerelease updates.

## Update source configuration

The updater defaults to the upstream `Anionex/banana-slides` repository. It reads `desktop/package.json:updateRepository` as the build-time default and then lets the per-install file override it:

```text
${app.getPath('userData')}/update-settings.json
```

Example fork configuration:

```json
{
  "automaticUpdatesEnabled": true,
  "updateRepository": {
    "owner": "FORK_OWNER",
    "name": "banana-slides-ru"
  }
}
```

Repository components are restricted to GitHub-safe name characters. On startup the desktop manager normalizes this setting and calls electron-updater's runtime `setFeedURL` with the selected GitHub owner/repo. Toggling automatic updates preserves the selected repository. Existing installs without the file remain pointed at upstream until configured.

The release workflow's **Configure fork update source** step derives the actual fork slug from `github.repository`, writes the package default, and rewrites the builder publish owner/repo in the ephemeral CI checkout. A local fork build must make the equivalent two configuration changes before packaging; do not leave a public fork build with upstream publish metadata.

## Check and fallback flow

1. Automatic checks start after 5 seconds and repeat every 6 hours. Manual checks use the same manager and never auto-download.
2. Packaged AppImage/Windows/macOS builds ask electron-updater for the selected GitHub feed. `autoDownload` and install-on-quit are disabled until the user chooses the download action.
3. A GitHub API releases request uses `User-Agent: BananaSlides/<version>` and sends `GITHUB_TOKEN` when that environment variable exists. The token is never logged or persisted.
4. If the API returns HTTP 403 or 429, `github-release-client.js` requests `https://github.com/<owner>/<repo>/releases.atom`. The minimal parser maps each release's title, release-tag link, and published/updated date to a release record. Because Atom has no asset list, the result is a manual update: the user is sent to the release page, where they choose the platform asset.
5. The release policy compares normalized semver, accepts prerelease updates only when the current build is prerelease, and requires a current-platform asset for API results. Same-version rebuilds can be offered when the release timestamp is newer than the local build metadata.
6. Unsupported packaged targets (including Debian packages) use the release-page fallback directly. Debian packages do not self-replace. A supported AppImage that was downloaded is installed only after the backend is stopped; `quitAndInstall` restarts the app and electron-updater replaces the AppImage according to its downloaded update state.

## Builder targets and required assets

Linux must retain the existing electron-builder AppImage target:

```yaml
linux:
  target:
    - target: AppImage
      arch: x64
```

`latest-linux.yml` is generated by electron-builder for the AppImage update feed; it is not a second `target` entry. Attach both the AppImage and `latest-linux.yml` to the **same GitHub Release** in the configured fork. With the current artifact pattern, the Linux installer is named like:

```text
BananaSlides-0.9.0-rc.7-ru.1-linux-x64.AppImage
latest-linux.yml
```

Do not rename or split the metadata file. The release workflow also uploads the existing Windows/macOS/deb artifacts and their `latest*.yml`/blockmap files where those targets are built. An AppImage release without its matching `latest-linux.yml` cannot complete an in-app self-update.

## Local build command

The normal release pipeline performs these steps. A local Linux build can use the equivalent sequence:

```sh
cd frontend && npm ci && npm run build
cd ../backend && uv sync && uv run pyinstaller banana-slides.spec --noconfirm
cd ../desktop && npm ci
npm run build:linux -- --publish never
```

The build writes artifacts under `desktop/dist/`. The full AppImage build is optional for this phase because Electron downloads and signing/package dependencies may be rate-limited. If it cannot run, retain the exact command and blocker in `PHASE15-REPORT.md`; do not substitute a fake artifact.

## Release checklist

- [ ] Merge and verify the newest upstream release tag; record it in `FORK.md`.
- [ ] Set the fork owner/name in `desktop/package.json:updateRepository` and `desktop/electron-builder.yml:publish`, or use the existing workflow step on the fork's CI run.
- [ ] Set `desktop/package.json` to `0.9.0-rc.7-ru.N` and create matching tag `v0.9.0-rc.7-ru.N`.
- [ ] Run backend tests and all desktop tests; smoke-test the AppImage from a read-only mount/layout.
- [ ] Build with `--publish never` locally, or review the workflow's draft release behavior before any authorized trigger.
- [ ] Attach `BananaSlides-<version>-linux-x64.AppImage` and `latest-linux.yml` to one fork release; verify the release page URL and assets.
- [ ] Publish only after explicit authorization. No publish or trigger is part of Phase 1.5.
